# 《字海残卷》Godot 2D 玩法核心迁移文档

## 1. 文档目的

这不是把当前 Babylon/Web 版本逐项翻译成 Godot 任务单。

这份文档只做一件事：

> 把《字海残卷》现在真正成立的玩法核心抽出来，重组为一份适合 Godot 2D 开发的实现基线。

因此它会主动做三件事：

- 保留已经成立的核心玩法骨架
- 去掉 UI、网页壳、Babylon 表现细节等非核心内容
- 用 Godot 2D 的开发方式重写系统边界，而不是照搬现有前端实现

## 2. 一句话定位

《字海残卷》的核心不是“汉字皮肤的幸存者”，而是：

> 一个以 `偏旁 -> 合字 -> 词技 -> 字路 -> 分段房间` 为主成长链的 2D 动作 roguelite。

底层是可读的即时战斗，上层是以汉字结构为规则的成长系统，中层是房间制 run 节奏。

## 3. 迁移原则

### 3.1 必须保住的东西

- 汉字不是主题皮肤，而是成长规则
- 战斗问题必须能被玩家读懂，而不是只靠数值硬压
- 房间制推进必须存在，不能退回成单 arena 无限刷波
- 成长必须围绕 `偏旁 / 合字 / 词技 / 字路` 串起来
- 内容必须尽量数据驱动

### 3.2 明确不要照搬的东西

- 启动器、门户页、Lore 页、排行榜、网页埋点
- Babylon 专属材质、shader、draw-call 优化细节
- 当前前端 overlay 结构、移动端 CSS 适配、触屏确认 UI
- 所有“因为浏览器/缓存/预览环境而存在”的代码

### 3.3 Godot 2D 的默认前提

- 默认视角直接采用俯视 2D
- 房间是 2D 战斗容器，不再假设 3D 地形表现
- 规则状态必须由游戏状态对象持有，而不是由节点表现层反推
- 先做可玩的系统表达，再补表现

## 4. 核心玩法三支柱

### 4.1 即时战斗层

玩家在房间中进行：

- 移动
- 自动攻击
- 主动技能解题
- 躲线、躲圈、躲区域
- 处理高优先级敌人与房间目标

这一层的目标不是花哨，而是让玩家稳定读出：

- 哪些敌人在逼位
- 哪些敌人在改写安全区
- 哪些威胁要求立刻转火
- 当前房间要优先完成什么

如果迁移到 Godot 后战斗变得更炫但更难读，那就是退步。

### 4.2 文字成长层

这是项目最不能丢的核心。

玩家成长链应保持为：

1. 升级或奖励获得 `偏旁`
2. 偏旁一方面立即给基础属性/行为修正，另一方面进入库存
3. 满足配方时，用库存偏旁合成 `合字`
4. 多余偏旁可继续投入已有合字，形成 `分支强化`
5. 合字达到足够深度后，晋升为 `词技`
6. `字路` 不直接替代上面系统，而是给后续掉落与构筑方向施加偏向

核心理解：

- `偏旁` 是资源
- `合字` 是构筑槽位里的功能单位
- `词技` 是高阶毕业结果
- `字路` 是 run 方向，不是普通被动

### 4.3 房间制 run 层

《字海残卷》必须是分段房间式推进，而不是一整局都在一个场地里刷怪。

单局的基本段落应该是：

1. 进入房间
2. 完成目标
3. 进入短决策窗口
4. 去下一房
5. 在关键节点遭遇守门怪 / 优先目标 / Boss
6. 获得更强的段落性回报

这里最重要的不是地图有多大，而是：

- 房间轮廓不同
- 房间目标不同
- 房间压力不同
- 房间之间有节奏切换

## 5. Godot 版推荐单局循环

这是建议迁移后的主循环，不要求逐帧复刻当前网页版本的触发时机。

### 5.1 房间内

- 玩家移动与自动攻击
- 击杀敌人、获取经验、拾取资源
- 应对房间 modifier、敌人组合、目标装置
- 使用主动技能解决走位或爆发问题

### 5.2 房间结算窗口

优先把构筑决策集中到这里，而不是拆散成大量网页式覆盖层：

- 处理升级得到的偏旁选择
- 处理可用合字
- 处理合字分支强化
- 如满足条件，处理词技晋升
- 在里程碑节点提供字路选择

### 5.3 房间间歇

- 奖励
- 事件
- 恢复
- 商人
- 进入下一房预览

### 5.4 段落节点

- `封 -> 守门怪 -> 奖励/通路`
- 或 `优先目标击破 -> 通路开启`
- 或正式 Boss 房

结论：Godot 版不必照搬“网页里每个 wave break 的具体 UI 节奏”，但必须保住“战斗 -> 短决策 -> 下一段压力”的节拍。

## 6. 当前应保留的核心系统定义

### 6.1 Hero，而不是只看 Character

为了避免歧义：

- `Hero` 指玩家角色，如 `书生`、`侠`
- `Character` / `合字` 指由偏旁构成的战斗功能单位

当前可直接作为 Godot 起点的 Hero 只有两个：

- `书生`
  - 无固定起手偏旁
  - 更适合完整体验文字成长链
  - 主动技偏向切线突进
- `侠`
  - 起手更明确
  - 更偏近身压制与护场
  - 主动技偏向定点控场

这两个已经足够构成 Godot vertical slice 的角色基线。

### 6.2 Radical

当前 live 玩法里，偏旁有两层意义：

- 立即给玩家基础增益
- 作为库存资源参与后续合字与分支强化

因此 Godot 版不要把偏旁做成“单纯经验天赋点”。

### 6.3 Character / Fusion

合字是 run 中期的主功能单位。

它们应该满足：

- 通过固定配方产生
- 占用有限槽位
- 一旦成型，就提供明确战斗行为
- 后续还能继续吃偏旁成长

当前 live 版本应以 `4` 个合字槽位作为默认基线，不沿用旧文档里的 `3` 槽设定。

附加原则：

- 默认 `4` 槽
- 特殊遗物可扩到 `5` 槽
- 每个合字都要有清楚战斗身份

### 6.4 WordSkill

词技不是普通升级，而是合字的高阶毕业。

当前合适的 Godot 逻辑是：

- 某个合字达到足够等级深度
- 满足指定分支条件
- 解锁对应词技

词技的作用是让玩家感觉：

> 我不是多拿了一个新技能，而是把原本那一个字养成了真正的 build 核心。

### 6.5 Route / Path

字路的职责是“提前给 run 定方向”。

它至少应影响：

- 后续偏旁倾向
- 后续遗物倾向
- 后续词技倾向
- 某些房间/事件回报倾向

Godot 版不要把字路做成一次性 stat buff，它应该是 run director 的偏向参数。

### 6.6 Relic

遗物是辅助层，不是主轴。

它的职责是：

- 放大某条字路
- 放大某种构筑节奏
- 给房间推进更强的中期差异

遗物不能盖过 `偏旁 -> 合字 -> 词技 -> 字路` 主链。

### 6.7 Field / 字境

`字境` 不应在 Godot 版里被做成纯表现层词汇。

它更适合被定义为：

- 房间当前的战斗环境状态
- 本房的危险区、机制区、控制区表达
- 章节/房间气质与战斗压力的统一承载层

换句话说，`Field` 在 Godot 里应是房间规则的一部分，可以驱动：

- 危险区行为
- 机关触发
- 安全区变化
- 房间 modifier 的持续压力

而不只是一个 shader 名字。

## 7. 敌人系统应该怎么抽象

Godot 迁移时，敌人应按“问题类型”建模，而不是按美术种类建模。

当前最值得保留的敌人语法是：

- `basic`：数量填充压力
- `swift`：近身节奏压力
- `tank`：拖时间、顶线
- `archer`：远程分心与拉扯
- `assassin`：惩罚站桩
- `cavalry`：强迫读线换位
- `ritualist`：重写安全区
- `phantom / elite`：中后期高压节点

这意味着 Godot 版先做的不是“很多怪”，而是“几类明确改写玩家决策的问题”。

## 8. 房间系统应该怎么抽象

### 8.1 房间模板先于章节美术

Godot 版房间模板应先定义：

- 可走区域
- 墙体/阻挡
- 出入口
- 刷怪锚点
- 目标锚点
- 标签

当前已经成立的模板思路可以直接沿用：

- 标准方房
- 横向长房
- 纵向长房
- 回字房
- 中央碑室
- 双岛房
- 斜裂房
- 门封房

### 8.2 房间目标必须是玩法核心

最小目标池建议：

- `clear_all`
- `survive`
- `destroy_seals`
- `defeat_priority_target`
- `defend_target`

其中 Godot 第一版至少应落地：

- `clear_all`
- `defeat_priority_target`
- `destroy_seals` 或 `survive`

### 8.3 当前 live 房间压力模型可直接转为 2D

当前四个房间 modifier 很适合迁移：

- `天`：安全区收缩
- `地`：反站桩落石
- `玄`：踩近触发机关
- `黄`：缓慢漂移的熔池

它们的价值不在 3D 视觉，而在：

- 改变站位
- 改变移动路径
- 改变房间优先级

这很适合 Godot 2D 继续做。

## 9. 守门怪与 Boss 的迁移原则

Boss/守门怪不是“大一点的精英怪”。

它们必须至少改变玩家对以下内容的阅读：

- 线
- 圈
- 区域
- 节点
- 输出窗口

因此 Godot 版第一只守门怪/Boss 应优先做“控场 + 拆点 + 破绽窗口”型，而不是纯追人近战型。

`封 -> 守门怪 -> 奖励` 这条结构值得保留，因为它天然把房间推进做成段落。

## 10. Godot 2D 推荐系统切分

下面是更适合 Godot 的责任分层，而不是当前前端文件结构。

### 10.1 RunDirector

负责：

- 单局 seed
- 房间顺序
- 章节/段落节奏
- 字路里程碑
- 间歇结算

### 10.2 RoomDirector

负责：

- 读取 RoomTemplate
- 安装 RoomModifier
- 生成目标物/出口/封印点
- 监听房间完成条件

### 10.3 CombatDirector

负责：

- 敌人生成
- 波次与刷新节奏
- 目标敌人/守门怪/Boss 管理
- 房间内胜负条件

### 10.4 ProgressionDirector

负责：

- 经验与升级
- 偏旁库存
- 合字生成
- 分支强化
- 词技晋升
- 字路与遗物偏向

### 10.5 ContentDatabase

负责加载数据定义：

- `RadicalDef`
- `FusionDef`
- `WordSkillDef`
- `RouteDef`
- `EnemyArchetypeDef`
- `RoomTemplateDef`
- `RoomModifierDef`
- `EncounterDef`

推荐优先使用 Godot `Resource` 或稳定 JSON，而不是把这些规则散落在节点脚本里。

## 11. 推荐数据骨架

下面不是最终语法，只是 Godot 版应保留的数据中心。

```gdscript
class_name RadicalDef
var id: String
var glyph: String
var affinity: String
var instant_effect: Dictionary
var recipe_hooks: Array[String]

class_name FusionDef
var id: String
var glyph: String
var ingredients: Dictionary
var slot_cost: int = 1
var base_behavior: String
var branch_scaling: Dictionary

class_name WordSkillDef
var id: String
var glyph: String
var base_fusion_id: String
var required_level: int
var branch_requirements: Dictionary
var upgrade_behavior: String

class_name RouteDef
var id: String
var glyph: String
var radical_bias: Array[String]
var relic_bias: Array[String]
var word_bias: Array[String]
var immediate_bonus: Dictionary

class_name RoomTemplateDef
var id: String
var bounds: Rect2
var blockers: Array
var spawn_anchors: Array[Vector2]
var objective_anchors: Array[Vector2]
var tags: Array[String]
```

关键点：

- 战斗规则从数据读取
- 节点只负责执行
- 不让 UI/动画成为玩法真源

## 12. Godot vertical slice 建议范围

不要一开始就把当前网页版本全部搬完。

第一段 vertical slice 建议只做：

- 2 个 Hero：`书生`、`侠`
- 8 到 10 个偏旁
- 6 个左右合字
- 2 个词技
- 3 条字路
- 5 类核心敌人
- 4 个房间模板
- 3 种房间目标
- 2 个房间 modifier
- 1 个守门怪或 Boss

只要这一版成立，就已经能验证项目最重要的问题：

- 汉字成长链在 Godot 2D 中是否仍然成立
- 房间制节奏是否比单 arena 更好
- 敌人与房间是否真的在共同出题

## 13. 明确延后项

以下内容不应进入 Godot 第一阶段核心迁移：

- 启动器与网页外壳
- 关键词注释面板与说明侧栏
- 房间编辑器完整移植
- 所有现有 Boss 全量迁移
- 所有现有 route/relic 内容一比一搬运
- Babylon 专用视觉演出

其中 `字形笔画遭遇` 值得保留，但更适合作为第二阶段内容系统，不应阻塞核心战斗迁移。

## 14. 最终判断标准

Godot 2D 版第一阶段算“玩法迁移成功”，不是看内容数量，而是看下面五件事是否成立：

1. 玩家能明确读懂战斗问题，并愿意主动换位、拆点、转火。
2. 偏旁选择会稳定导向不同合字与词技，而不是只涨数值。
3. 一局 run 能形成“我这局养成了哪个字、走了哪条路”的记忆。
4. 房间差异来自空间与目标，而不是只换怪物数值。
5. 守门怪/Boss 能制造机制性输出窗口，而不是单纯血更厚。

如果这五点成立，《字海残卷》的核心就已经成功迁到 Godot 2D 了。
